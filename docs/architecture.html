System Architecture

Factory Inventory Management System

A full-stack demo application: a Vue 3 single-page frontend talking over HTTP/JSON to a Python FastAPI backend, which serves read-only data loaded from static JSON files into memory. No database.

Tech Stack

Frontend

Vue 3 SPA

  • Vue 3.4 · Composition API
  • vue-router 4.3 (history mode)
  • axios 1.6 for HTTP
  • Dev server on port 3000
Backend

FastAPI Service

  • FastAPI 0.110 + Uvicorn
  • Pydantic 2.5 validation
  • Python ≥3.11, run with uv
  • Serves on port 8001 · CORS open · docs at /docs
Data Layer

In-Memory Mock Data

  • 7 JSON files in server/data/
  • Loaded once at import by mock_data.py
  • No DB · no persistence (resets on restart)
Build & Tooling

Vite + uv

  • Vite 5.2 + @vitejs/plugin-vue
  • uv for Python env/deps
  • Backend tests: pytest + FastAPI TestClient

System Architecture & Data Flow

Two independent processes. The browser-hosted SPA (:3000) issues HTTP requests via axios to the FastAPI service (:8001), which reads from in-memory globals hydrated from JSON files at startup.

  1. User changes a dropdown in FilterBar.vue, mutating a shared ref in the useFilters composable (e.g. selectedLocation = 'Tokyo').
  2. A watching view (e.g. Dashboard.vue) maps state via getCurrentFilters() and calls api.getDashboardSummary(filters).
  3. api.js builds http://localhost:8001/api/dashboard/summary?warehouse=Tokyo and issues an axios GET.
  4. FastAPI routes to the handler, which runs apply_filters() / filter_by_month() over the in-memory globals.
  5. Handler computes aggregates and returns JSON; axios resolves response.data into reactive refs and Vue re-renders.

API Endpoints

All endpoints are read-only GET. Filter params accept all (ignored) or a specific value.

MethodPathFilters / ParamsReturns
GET/api/inventorywarehouse, categoryFiltered inventory items
GET/api/inventory/{id}—Single item (404 if missing)
GET/api/orderswarehouse, category, status, monthFiltered orders (month/quarter)
GET/api/orders/{id}—Single order (404 if missing)
GET/api/demand—Demand forecasts
GET/api/backlog—Backlog items + has_purchase_order join
GET/api/dashboard/summarywarehouse, category, status, monthAggregated KPI totals
GET/api/spending/summary—Spending summary object
GET/api/spending/monthly—Monthly spending array
GET/api/spending/categories—Spending by category
GET/api/spending/transactions—Recent transactions
GET/api/reports/quarterly—Per-quarter computed stats
GET/api/reports/monthly-trends—Per-month computed trends
Known gap: The frontend api.js also references write endpoints — /api/tasks (GET/POST/PATCH/DELETE) and purchase-order routes (POST /api/purchase-orders) — that are not implemented in the backend. Those features are client-side stubs; purchase_orders.json ships empty.

Data Files

inventory.json

  • SKU, category, warehouse, quantity, reorder point, unit cost

orders.json

  • Order number, customer, items, status, dates, total value

demand_forecasts.json

  • Current vs. forecasted demand, trend, period

backlog_items.json

  • Needed vs. available qty, days delayed, priority

spending.json

  • Summary + monthly + category spending (one object)

transactions.json

  • Date, description, category, warehouse, amount, vendor

purchase_orders.json

  • Empty array — populated only by unimplemented write route
